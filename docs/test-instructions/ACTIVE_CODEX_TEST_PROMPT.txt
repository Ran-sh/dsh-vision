2. WHY THIS RETEST EXISTS
============================================================

The previous full regression completed meaningful coverage but was NOT release-ready because:

NEW-R1 — HIGH — sent/history image preview UX
- draft preview: PASS
- sent historical thumbnail/gallery: FAIL

- compare case reached the previous 1024 output-token cap before completing required evidence.

The new implementation is intended to fix exactly those two product-layer issues.

NEW-R1 design expectation:

- user conversation text still contains only neutral image markers;
- successful image sends are committed separately to a durable host-side display ledger;
- the browser reads only opaque committed batch metadata for the active session;
- preview bytes use a safe preview route addressed by opaque batch id + ordinal;
- raw attachment ids/raw routes do not return to conversation text;
- preview ledger commits only after the conversation prompt succeeds.

FR-001 design expectation:

- task-aware compare budget remains around its policy value (currently 2200);
- default provider hard cap is now 3000 instead of 1024;
- effective output cap is therefore not silently flattened to 1024 by default;
- an explicitly configured lower user cap remains authoritative.

7. NEW-R1 — ONE-IMAGE HISTORY UX
============================================================

Use one controlled PNG.

Procedure:

1. Paste/attach the image but do not send yet.
2. Confirm draft preview exists.
3. Send an image-dependent user request.
4. Confirm the user message is admitted exactly once.
5. Confirm the historical user row now contains a visible image thumbnail after send.
6. Confirm the thumbnail corresponds to the sent image, not another session/batch.
7. Click the thumbnail.
8. Confirm a usable larger/full preview opens.
9. Close the viewer normally.
10. Confirm the main model can still invoke `understand_image` and return correct visual evidence.

PASS requires all ten.

Inspect visible user message text. Allowed:

- user's own text
- `已附加图片。`

Forbidden in user-visible conversation text:

- `attachmentId`
- `sha256:`
- `/image-mind/raw/`
- attachment JSON
- dimensions/byte metadata
- HTML routing comment
- `understand_image`
- internal tool-routing instruction

A browser image `src` may use an opaque `/image-mind/preview/...` route internally. That alone is not leakage. Fail secrecy if raw attachment identity/metadata is restored into conversation text or if the preview route itself embeds the raw attachment id.
